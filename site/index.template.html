Controlled Evaluation of Workflow Graphs and Routing for Code-Repair Agents

Yiwen Lu · University of Notre Dame

We turn a coding agent's harness into a searchable graph and show that checking supplied tests, returning failure feedback and retrying improves repair success on the tested bug-fixing tasks.

One task from the study. In the DeepDiff library, comparing two sets reports the wrong direction: items that were added show up as removed, and removed items as added. The agent receives this issue text and the repository with the bug, edits the code with shell commands, and hands in a patch. The patch counts as a repair when the project's grading tests pass.

The harness is the program around the language model. Written as a graph, its nodes perform steps (a stretch of agent conversation, or a program such as a test run) and its edges choose the next step from the outcome the last one returned: the test run returned fail, so go back to editing. Edges carry no data: the conversation, the repository working copy and the latest feedback live in a state that every node reads and writes. Our compiler generates {{distinct}} graphs that pass static checks; the engine runs any of them, and search decides which ones to run.

2 · What search and per-task selection added on top

With {{distinct}} graphs to choose from, harness design becomes a search problem: spend a fixed number of agent runs deciding which graph to try on which task, then return one graph (the loop is drawn in Figure 8). With Qwen3.8-27B we split the tasks into {{q_tasks}} for search, {{s_tasks}} for selection and {{c_tasks}} held out for confirmation. Search and selection used visible grading tests; confirmation and the per-task policies were evaluated with both visible and hidden tests. Searches ran on a table of stored results and live; the best candidates were compared on the selection tasks; the winner was frozen and then run on the held-out tasks, which no earlier step had seen.

With grading tests visible, the graph selected by search differed from check-and-retry by {{c_d}} points on the held-out tasks.It repaired {{c_top}} against {{c_h04}} (95% interval of the difference {{c_lo}} to {{c_hi}}). The held-out tasks are {{c_old}} from the {{c_old_repos}} repositories that also supplied search tasks and {{c_new}} from {{c_new_repos}} withheld repositories ({{c_runs}} scored runs for the three graphs, visible and hidden). The selected graph was better on {{c_better}} tasks and worse on {{c_worse}}, and under the rule fixed before the run the result excludes an improvement of {{c_margin}} points or more. On the {{s_tasks}} selection tasks, as the best of {{s_graphs}} candidates, it had led by {{s_d}} points ({{s_lo}} to {{s_hi}}). It averaged {{c_calls_top}} model calls per run against {{c_calls_h04}}, and {{c_tok_top}} against {{c_tok_h04}} tokens.

The selected graph extends check-and-retry with two side paths: {{s_extras}} . Its nodes are solve, check, reflect (the model reads the failure output and writes down the cause) and stall_compact, a compact node (the model replaces the conversation with a summary). Its edges: solve → check on done; check → END, which submits the patch, on pass; check → reflect on fail, then reflect → solve, with at most two retries; solve → stall_compact on stalled (20 steps without an edit), then stall_compact → solve.

On {{f_tasks}} fresh tasks of the kind where it had looked better, the selected graph differed from check-and-retry by {{f_d}} points.It repaired {{f_top}} against {{f_h04}} (95% interval of the difference {{f_lo}} to {{f_hi}}). SWE-smith builds some tasks by combining several planted defects in one file or one module. A breakdown made after confirmation found the selected graph {{x_d}} points ahead (95% interval {{x_lo}} to {{x_hi}}) on the {{x_n}} such tasks among the selection and confirmation tasks; {{x_sel}} of them were selection tasks. We tested this once on new tasks, with the rules written before any run: {{f_tasks}} tasks ({{f_file}} combining defects in one file, {{f_module}} in one module), {{f_per}} from each of {{f_repos}} repositories no earlier step had used, {{f_runs}} scored runs. The selected graph was better on {{f_better}} tasks and worse on {{f_worse}}, the result excludes a gain of {{f_margin}} points under the pre-set rule, and leaving out any one repository gives a difference between {{f_loo_lo}} and {{f_loo_hi}} points. The selected graph used {{f_tok}} fewer tokens per run (95% interval {{f_tok_lo}} to {{f_tok_hi}} fewer), with similar observed repair rates.

Every live search kept the enforced check: all {{ls_runs}} ended on a graph that contains it.Each search starts from the plain loop and proposes a change to one design variable at a time. A step runs the current and the changed graph on the same {{ls_step_tasks}} tasks and keeps the change if the changed graph repairs more of them. {{ls_per}} searches chose the next change at random and as many chose it from the way the last runs had failed; each spent {{ls_budget}} scored agent runs ({{ls_steps}} steps). In {{ls_gate_rejected}} searches the first proposal to add the check was rejected before a later one was accepted, and adding it was the first change proposed in {{ls_gate_first}}. The {{ls_runs}} returned graphs are all different: besides the check, {{ls_retries3}} allow up to three retries, {{ls_compact}} summarize the conversation past a length threshold, and {{ls_nudge}} remind the agent after a stall (Table 3).

5 · How this fits published work

  • Published search gains depend on the task, the baseline and the evaluation design. AFlow reports a 5.7% average improvement over state-of-the-art baselines on six benchmarks with validation and test splits. On TerminalBench-2 with Claude Opus 4.6, Meta-Harness reports 76.4%, against 74.7% listed for the hand-engineered Terminus-KIRA, with search and final evaluation on the same 89 tasks. That work studies discovery on one benchmark; our confirmation evaluates transfer to {{c_tasks}} and {{f_tasks}} tasks withheld from search and selection.
  • Retrying on provided tests is a strong baseline elsewhere too. In AI Agents That Matter, a baseline that only reruns GPT-4 up to five times while the provided tests fail reaches 92.0% on HumanEval, and the authors ask for cost-controlled comparisons and held-out tasks.
  • Tests that fail before a fix often do not pass after it. Agentless keeps a generated reproduction test when it reports the bug on the original repository: 213 of 300 issues receive one, and only 94 of these tests report the issue resolved after the ground-truth patch. On SWT-Bench-Lite, SWE-Agent+ with GPT-4 writes an initially failing test for 46.4% of issues, and for 18.5% a test set that detects the bug with no failure after the reference fix; in a separate experiment, filtering SWE-Agent's fixes with generated tests yields 47.8% precision (the share of retained fixes that are correct) and 20% recall (the share of correct generated fixes retained). Our screen separately measures rejection of the reference and of grader-accepted patches, against requirements fixed in advance.
  • Budget moves results. SWE-agent's authors conjectured, from run lengths under a $4 cap, that a larger budget would not substantially raise performance; measured directly in our setting, the final patch of a {{a1_cap}}-call run is a repair {{a1_d}} points more often than its state after call {{a1_cutoff}}. In one analysis of a multi-agent research system, token usage alone explains 80% of the performance variance on BrowseComp.
  • Sub-agents are a separate question, which this project did not test. On a 100-task sample of SWE-bench Verified with three coding agents, Li et al. find that running sub-agents concurrently gives no improvement, and report 1.41 to 3.31 times the tokens of sequential execution across their benchmarks; Yuan et al. find that tightly coupled trajectories are often better handled by a single agent.
  • The tasks have a known limit. SWE-smith's issue texts are written by a language model from the bug patch, the list of failing tests and the source of one of them, with no check for underspecified text. Its authors state that the released dataset does not yield instances appropriate for evaluation. We remove the designated failing-test files in the hidden condition, but have not validated issue texts for ambiguity or leakage, or established how faithful the synthetic tasks are to real issues.

6 · Build and inspect a harness

The engine has six node types. Before a graph runs, static checks confirm that every outcome of every node has an edge, every node can be reached, loops are bounded by visit limits, and each node's inputs are written on every path that leads to it. Everything a later node needs lives in the shared state (the conversation, the repository working copy and the latest feedback), so edges carry no data.

Node typeWhat it doesOutcomes it can return
agentThe model issues shell commands one at a time until it says it is done. Its role sets the instruction: solve, reproduce the bug, fix after reproducing, or verify before submitting.done · step limit · context too long · stalled
planThe model reads the file list and writes a short plan.next
checkA program runs the project's tests on the current patch.pass · fail
reflectThe model reads the failure output and writes down the cause.next
resetA program restores the code and clears the conversation, keeping only the note on the cause.next
compactThe model replaces a long conversation with a summary.next

The hand-designed graphs differ in a small number of decisions. Writing those decisions down as nine design variables turns the collection into a space: choose a value for each variable and a compiler assembles the graph. Set the variables below and the graph is redrawn.

How a setting becomes a graph

  1. Main line. The compiler lays out the nodes that are switched on in a fixed order: plan, reproduce, edit, summarize, self-review, run tests, submit. Consecutive nodes are joined by the edge for the normal outcome (done, next, pass).
  2. Side loops. Three outcomes lead off the main line and back to the editing node: fail from the test check (variables ⑥ and ⑦ decide what lies on the way back and how often the edge is followed), context too long (variable ⑧), and stalled (variable ⑨).
  3. Limits. Every node on a loop gets a visit limit computed from the retry settings, so each graph is guaranteed to end. The static checks above then run on the result.
  4. Counting. Variables ⑥ and ⑦ do nothing unless ⑤ is on, so those settings are merged:
①②③④: 2×2×2×3 = 24    ⑤⑥⑦: 1 without the check + 3×3 with it = 10    ⑧⑨: 3×5 = 15    24 × 10 × 15 = {{distinct}}

Of the {{raw}} raw settings, {{distinct}} graphs remain. All are structurally different from one another, all pass the static checks, and they range from 1 to {{max_nodes}} nodes. The {{n_hand}} hand-designed graphs are {{n_hand}} points of this space. The compiler is harness_graph/grammar.py; the drawing on this page is a JavaScript port of it, checked against the Python version on every setting.

Details and limits
  • Tasks and models. All tasks are SWE-smith bug fixes in Python repositories with an injected bug. The first study (section 1, Figures 2 and 3, Table 2) uses gpt-6.1-terra and gpt-6-luna, two models from one vendor, on {{n_confirm}} confirmation tasks from {{n_conf_repos}} repositories; search, confirmation, the follow-up and the check screen use Qwen3.8-27B with thinking disabled. The three withheld repositories ({{c_new}} tasks) support a claim about those three. The follow-up covers tasks of two SWE-smith strategies from repositories with at least 60 such tasks, a test suite that runs in under two minutes and a grader verified task by task, so its result is about this mixture of {{f_repos}} repositories with visible tests. Rows of Table 1 differ in repositories, task selection and runs per task, so the larger lead in the follow-up does not isolate the effect of the kind of task; there the plain loop also ran after the other two graphs.
  • What checking means. With visible tests the check node runs the same tests the grader uses, an executable specification of the task; the gains show what a harness does when such a specification exists. Check-and-retry is a package (a check, the failure text sent back and up to two retries), compared at its observed cost, not at matched cost. That most rescued runs had stopped with a failing check is an observation from the logs, not a tested mechanism.
  • What search covers. Confirmation tests the one graph returned by this search-and-selection procedure; the bound of {{q_bound}} points covers the {{q_graphs}} measured graphs, not the whole grammar, and an improvement smaller than the upper ends of the intervals ({{c_hi}} points in confirmation, {{f_hi}} in the follow-up) remains compatible with the results. Between {{r_reuse_lo}} and {{r_reuse_hi}} of the {{r_budget}} replay draws repeat a stored result, so Figure 7 describes this table rather than ranking the procedures in general. {{u_n}} of the {{q_tasks}} search tasks were also used in the first study and the live searches ran on these tasks, so their keeping the check is not independent evidence for it. The {{distinct}} graphs are structurally different, but two of them can behave identically on a task; every graph has one agent, and the branch thresholds (16k tokens, 20 steps) are set by hand. The per-task policies cover two policies over three graphs. Choosing changes from failures uses a hand-written table from the way a run ended to a remedy, and for each seed the two ways of choosing share their first proposed change.
  • Statistics. For the Qwen3.8-27B analyses, intervals redraw tasks inside repositories and keep the observed mix of repositories, so they leave out the uncertainty of sampling other repositories; the first study bootstraps tasks. The selection lead is the largest of {{s_graphs}} noisy estimates and its interval includes zero. The comparison of the two ways of choosing changes covers {{ls_per_l}} searches each and conditions on those seeds. In held-out confirmation with hidden tests each task ran once, and the pairwise intervals of Table 4 are individual intervals, not simultaneous bounds or a margin fixed in advance; the visible-versus-hidden comparison was chosen after the results were seen. The lead on the {{w_n}} search tasks new to this project has an interval that includes zero; whether it is smaller because the other tasks had been used before or because the plain loop leaves less to gain there is open. The leads on the selection tasks ({{s_k}} points) and on those new search tasks ({{w_d}} points) are separate samples with two runs and one run per task.
  • The check screen. It is a screen on development tasks (the search tasks) with one 27B model in {{pt_repos}} repositories, not a repair experiment, and it does not cover other models or other ways of writing checks. Rates average first within a task (over its two checks and its patches) and then over tasks; the false-rejection rates count only delivered checks ({{pt_ref_n}} and {{pt_acc_n}} tasks for version 2). The wrong patches are those this model produced in earlier runs, and “correct” means accepted by the grader. The thresholds apply to point estimates: the detection intervals include the required {{pt_th_det}} for both versions, and the verdict rests on the two false-rejection rates, whose intervals lie entirely above their limits. The two versions differ in the runner, the instructions, a sentence about the response budget and the option to decline, so their numbers are a side-by-side description; the corrected-runner column is a sensitivity result.
  • Labels used for diagnosis. The issue-coverage labels come from one model (gpt-6.1-terra) on {{a_n}} of the {{q_tasks}} search tasks, without human review, and do not give the share over all tasks. The reasons why checks rejected the bug-free repository come from two language-model raters on cases selected by their failure; some disagreements with the issue are literal ones about formatting, and the reading leaves every earlier comparison between graphs unchanged. How unsolved hidden-test runs ended was computed after the confirmation results were seen, and the way a run ends is a label, not a cause.
  • Data qualifications. An audit made for the check screen found leftovers in task containers: in parso a bug-free copy of the package is installed, and in funcy a backup copy of one grading test file remains. This affects {{lk_s2}} of the {{lk_s2_n}} confirmation tasks of the first study, {{lk_search}} of the {{pt_all}} search tasks, none of the selection tasks and {{lk_s5}} of the {{lk_s5_n}} held-out tasks, in every graph alike; whether an agent used them was not examined. The audit covered the {{lk_audited}} repositories of the search tasks; the three withheld repositories ({{lk_s5_unaudited}} tasks) and the follow-up repositories were not audited, and the check screen left the affected tasks out. Stage 1 of the search retained {{q_overruns}} deadline overruns; restoring the {{q_replaced}} replaced outcomes leaves check-and-retry's advantage unchanged and makes the best sampled alternative tie it. {{f_late}} follow-up runs went past the one-hour limit ({{f_late_h04}} of check-and-retry, {{f_late_top}} of the selected graph) and were kept, as the plan says. The per-task policies were fitted on the stage-1 runs and inherit their qualifications. Other process deviations (server load in stage 1 and the rerun check still owed, a five-minute overlap of two jobs in confirmation, the follow-up's split jobs, the commit time of its task file and one early health check) are recorded in the protocol.
  • The audit of failed runs and the cap extension. Both are exploratory. How a run ended and how many checks it reached are labels, not causes, and the counts of tasks solved in all, none or some of four runs pool check-and-retry with the selected graph. The cap extension uses {{a1_tasks}} of the {{f_tasks}} follow-up tasks, sampled without consulting outcomes, one model and one graph; every graph in sections 1 and 2 ran under the 50-call cap, so the result does not explain why search found no better graph and gives no ranking of graphs at {{a1_cap}} calls; {{a1_bsolved}} of the {{a1_boundary}} runs that reached the continuation boundary after call {{a1_cutoff}} already held a solved patch; {{a1_grade_timeouts}} gradings of the state after call {{a1_cutoff}} timed out, both for one task, and count as unsolved. No losses were observed, which is not a guarantee that continuing is safe. The extension does not compare continuation with restarting or another graph, and benefits beyond {{a1_cap}} calls were not measured. The perfect-selector figure covers three stored candidates per task and is not a ceiling for other systems, the gap by number of defect files is an association, and the hidden-test observations do not show that missing information explains most failures or that another execution structure could not help.
  • The benchmark. SWE-smith was built to produce training data, and its authors state that as released it does not yield instances appropriate for evaluation. We remove the designated failing-test files in the hidden condition, but have not validated issue texts for ambiguity or leakage, or established how faithful the synthetic tasks are to real issues. We verify each task's grader with two controls (the reference fix is graded as a repair, the unchanged buggy code is not). Our visible condition explicitly supplies the grader's tests.
  • Costs. Costs are per run and leave out the runs spent on search and selection. In confirmation with visible grading tests, the token difference between the selected graph and check-and-retry is not established (ratio {{c_tok_ratio}}, 95% interval {{c_tok_lo}} to {{c_tok_hi}}). The follow-up's token reduction is a secondary observation; it does not establish lower latency or cost, or that summarizing the conversation causes it.
