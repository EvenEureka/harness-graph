Adaptive Graph Harness Optimization for LLM Agents

Yiwen Lu · University of Notre Dame

A coding agent is a language model plus the program around it, the harness: what the model is asked to do first, when its work is checked, and what happens after a failed check. This project writes the harness as a graph, compares hand-designed graphs on bug-fixing tasks, and searches a space of 3,600 graphs for better ones.

1 · A harness as a graph

A node is one unit of execution: a stretch of agent conversation, or a deterministic program such as a test run. It reads the shared state, writes to it, and returns an outcome label such as done, pass or fail.

An edge is a control rule: node X returned outcome r, so run node Y next. Edges carry no data. Everything a later node needs is in the shared state: the conversation, the repository working copy, and the latest feedback.

The engine has six node types. Before a graph runs, static checks confirm that every outcome of every node has an edge, every node can be reached, loops are bounded by visit limits, and each node's inputs are written on every path that leads to it.

Node typeWhat it doesOutcomes it can return
agentThe model issues shell commands one at a time until it says it is done. Its role sets the instruction: solve, reproduce the bug, fix after reproducing, or verify before submitting.done · step limit · context too long · stalled
planThe model reads the file list and writes a short plan.next
checkA program runs the project's tests on the current patch.pass · fail
reflectThe model reads the failure output and writes down the cause.next
resetA program restores the code and clears the conversation, keeping only the note on the cause.next
compactThe model replaces a long conversation with a summary.next

2 · What the hand-designed graphs showed

Seventeen graphs were written by hand for short bug-fixing tasks from SWE-smith (real Python repositories with an injected bug) and run with two models. After a pilot on 27 development tasks, nine graphs were run on {{n_confirm}} confirmation tasks in two conditions: with the failing tests visible in the repository, so a check node can run them, and with those tests hidden. Two more graphs were added for the comparison in Table 1.

With tests visible, checking the patch and returning failures raises the repair rate.From {{t_h01}} to {{t_h04}} for gpt-6.1-terra ({{t_delta}} points, 95% interval {{t_lo}} to {{t_hi}}; better on {{t_wins}} tasks, worse on {{t_losses}}) and from {{l_h01}} to {{l_h04}} for gpt-6-luna ({{l_delta}} points, {{l_lo}} to {{l_hi}}; better on {{l_wins}}, worse on {{l_losses}}). The price is {{t_calls}} and {{l_calls}} more model calls.

With tests hidden, no graph showed an improvement over the plain loop.The failing tests are then unavailable to the check node, although its checks of edits, compilation, reproduction scripts and the remaining tests can still give feedback. Across the eight other graphs measured in this condition, differences to the plain loop ranged from {{hid_min}} to {{hid_max}} points, every interval including zero.

Enforcing the check does more than suggesting it.Asking the model to review its own work before submitting changed the repair rate by {{t_sv}} points for gpt-6.1-terra and {{l_sv}} for gpt-6-luna, less than the enforced check for both (Figure 3). 3 · From 17 hand-drawn graphs to a space of 3,600

The hand-designed graphs differ in a small number of decisions. Writing those decisions down as nine design variables turns the collection into a space: choose a value for each variable and a compiler assembles the graph. Set the variables below and the graph is redrawn.

How a setting becomes a graph

  1. Main line. The compiler lays out the nodes that are switched on in a fixed order: plan, reproduce, edit, summarize, self-review, run tests, submit. Consecutive nodes are joined by the edge for the normal outcome (done, next, pass).
  2. Side loops. Three outcomes lead off the main line and back to the editing node: fail from the test check (variables ⑥ and ⑦ decide what lies on the way back and how often it may be taken), context too long (variable ⑧), and stalled (variable ⑨).
  3. Limits. Every node on a loop gets a visit limit computed from the retry settings, so each graph is guaranteed to end. The static checks of section 1 are then run on the result.
  4. Counting. Variables ⑥ and ⑦ do nothing unless ⑤ is on, so those settings are merged:
①②③④: 2×2×2×3 = 24    ⑤⑥⑦: 1 without the check + 3×3 with it = 10    ⑧⑨: 3×5 = 15    24 × 10 × 15 = {{distinct}}

Of the {{raw}} raw settings, {{distinct}} graphs remain. All are structurally different from one another, all pass the static checks, and they range from 1 to {{max_nodes}} nodes. The 17 hand-designed graphs are 17 points of this space. The compiler is harness_graph/grammar.py; the drawing on this page is a JavaScript port of it, checked against the Python version on every setting.

4 · Searching the space: results

With a space of graphs, harness design becomes a search problem: given a fixed number of agent runs, which graph should be tried on which task next, and which graph should be returned at the end? The returned graph is then scored on tasks the search never saw.

The search experiment uses Qwen3.8-27B with thinking disabled: search and selection use visible tests, while confirmation and the choice of a graph per task are evaluated with both visible and hidden tests. Its tasks are split into 188 for search, 56 for selection and 232 held out for confirmation. All six stages are finished; the confirmation tasks were first run in stage 5, after the graph and the policies under test had been fixed.

In short.Check-and-retry produced a clear improvement over the plain loop when tests are visible. The graph returned by the tested search-and-selection procedure showed no detectable additional repair benefit, and its interval excluded a gain of five points. Neither tested policy for picking a graph per task demonstrated an additional benefit.

Stage 2 · Four search procedures replayed on the table

At {{r_budget}} table draws, all four procedures returned graphs with a higher average held-out repair rate than the plain loop and a lower one than check-and-retry.The procedures are uniform allocation, successive halving, Thompson sampling, and Thompson sampling with a linear model over the design variables. For each of {{r_splits}} random halvings of the tasks, a procedure searches using {{r_budget}} draws from the stored results on one half, returns one graph, and that graph is scored on the other half (Figure 5).

Stage 3 · Local search over all {{distinct}} graphs with live agent runs

All ten searches ended on a graph with the enforced test check.Each search starts from the plain loop and proposes a change to one design variable at a time. A step runs the current graph and the changed graph on the same 16 tasks and keeps the change if the changed graph repairs more of them. Five searches chose the next change at random and five chose it from the way the last runs had failed. All {{ls_runs}} completed {{ls_budget}} scored agent runs ({{ls_steps}} steps), with no engine errors or deadline overruns. All {{ls_runs}} eventually accepted the enforced check and kept it in their final graph; {{ls_gate_rejected}} rejected their first proposal to add it before accepting a later one, and adding the check was the first change proposed in {{ls_gate_first}}.

The ten returned graphs are all different.Besides the check, {{ls_retries3}} allow up to three retries after a failed check, {{ls_compact}} summarize the conversation past a length threshold, and {{ls_nudge}} remind the agent after a stall (Table 3). Scores observed during a search are not independent estimates of how its graph does on unseen tasks, because the search used those observations to decide which changes to keep. Each returned graph was therefore run on the 56 selection tasks, which no search had used (stage 4).

Stage 6 · A graph per task

A last question is whether different tasks should get different graphs. Three policies were fitted on the search tasks and frozen before stage 5: always one graph (the fit chose check-and-retry), a rule on whether tests are visible (the fit chose the plain loop when they are hidden and the selected graph when they are visible), and a linear model on visibility and features of the task text. Each was scored on the {{rt_units}} pairs of a confirmation task and a test condition, with the two conditions weighted equally.

Neither policy that picks a graph per task demonstrated an improvement over always using check-and-retry.Always check-and-retry repaired {{rt_fixed}}; the visibility rule {{rt_rule}}, a difference of {{rt_rule_d}} points (95% interval {{rt_rule_lo}} to {{rt_rule_hi}}); the model on task features {{rt_feat}}, a difference of {{rt_feat_d}} points ({{rt_feat_lo}} to {{rt_feat_hi}}).

What happens next

Visible-test confirmation left limited room above check-and-retry: it already repaired {{c_h04}}, which makes a five-point gain demanding. Search and selection were run with visible tests only, and the mechanisms they selected showed no demonstrated advantage with hidden tests either. With hidden tests, between {{d_wrong_lo}} and {{d_wrong_hi}} of the {{d_uns_lo}} to {{d_uns_hi}} unsolved runs of each graph ended with the agent submitting a patch that was wrong. These exploratory figures point to unreliable verification when no failing test is supplied as a candidate bottleneck.

The next phase tests one question: when no tests are given, does a graph that writes its own executable check and enforces it repair more bugs than check-and-retry at the same total inference cost? It starts with two premise tests on the search tasks, each with a stop rule written beforehand: whether the task descriptions support what the grader demands, and whether model-written tests reject known wrong patches without rejecting correct ones. Only if both pass is the repair comparison run, and only if that shows a gain of at least five points is it confirmed on fresh tasks.

5 · Scope and limits

  • The results in section 2 come from one benchmark family (short bug fixes in nine Python repositories, {{n_confirm}} confirmation tasks) and two models from one vendor.
  • In the visible-test condition the check runs the same tests the grader uses, so it is an executable specification of the task. The result says what a harness can do when such a specification exists; it does not show that a check built from weaker signals would help.
  • In section 2, with hidden tests the study found no improvement. It was not sized to show that the graphs are equivalent.
  • In section 2, check-and-retry costs more: {{t_calls}} and {{l_calls}} more model calls, {{t_tokens}} and {{l_tokens}} more tokens. The comparison is not at matched cost.
  • Why the enforced check helps (most rescued runs had stopped with a failing check) is an observation from the logs and a hypothesis, not a tested mechanism.
  • 3,600 counts graphs that are structurally different. Two different graphs can behave identically on a given task.
  • Every graph has a single agent, and the branch thresholds (16k tokens, 20 steps) are set by hand.
  • Section 4 uses one model with thinking disabled and one benchmark family. Stages 1 to 3 used only the search tasks and stage 4 used {{s_tasks}} further tasks from eight of the same repositories; only stages 5 and 6 are confirmation results.
  • Stage 5 tests the one graph returned by this search-and-selection procedure. It does not show that no graph among the {{distinct}} is better than check-and-retry, and an improvement smaller than {{c_hi}} points remains compatible with the result.
  • Check-and-retry is a package: a check, the failure text sent back, and up to two retries. Stage 5 does not separate these parts, and the comparison with the plain loop is not at equal cost.
  • The withheld repositories are three. The result on them supports a claim about these three, not about new repositories in general.
  • With hidden tests each task was run once. Each individual 95% interval for a comparison of two graphs on all tasks lies within −4 to +4 points. These are not simultaneous bounds, and four points was not a margin fixed in advance. The comparison of the visible-test lead with the hidden-test lead was not fixed in advance either.
  • The token difference between the selected graph and check-and-retry with visible tests is not established (ratio {{c_tok_ratio}}, 95% interval {{c_tok_lo}} to {{c_tok_hi}}). Costs are per run and leave out the runs spent on search and selection.
  • The figures on how unsolved hidden-test runs ended were computed after the confirmation results were seen. The way a run ends is a label, not a cause, and the next phase may find that model-written checks do not help.
  • Stage 6 tests two policies over three graphs. Other policies, or a larger set of graphs to pick from, were not tested. The policies were fitted on the stage-1 runs with visible tests, so their fitting data carry the qualifications on concurrency and replaced runs described below.
  • The intervals of stages 5 and 6 redraw tasks inside repositories and keep the observed mix of repositories. They do not measure the uncertainty from sampling other repositories.
  • In stage 5 one hidden-test job started about five minutes before the last visible-test job finished, instead of strictly after both. At most two jobs were active at any time.
  • The lead of the selected graph on the selection tasks is the largest of {{s_graphs}} noisy estimates and its interval includes zero. The comparison of the two ways of choosing the next change covers five searches each; its interval does not include what would change if the searches were run again with other seeds.
  • The lead of check-and-retry over the plain loop on the {{s_tasks}} selection tasks ({{s_k}} points) and on the {{w_n}} new search tasks ({{w_d}} points) are two separate samples from the same repositories, measured with two runs and one run per task. They do not contradict each other, and the page does not claim that the lead grew.
  • {{u_n}} of the {{q_tasks}} search tasks were also used in the study of section 2, and the live searches ran on these same {{q_tasks}} tasks. That every search kept the enforced check is therefore not independent evidence that the check helps on new tasks.
  • The {{w_n}} tasks new to this project come from the same repositories as the others, and the interval for the lead of check-and-retry on them includes zero. Two readings of the smaller lead are not separated: that the other tasks had been used before, and that there is less to gain where the plain loop already repairs more.
  • Stage 2 compares four implementations on one table with one run per cell. Between {{r_reuse_lo}} and {{r_reuse_hi}} of the {{r_budget}} draws repeat a stored result. The averages describe this table; they do not rank the procedures in general, and the bound of {{q_bound}} points covers the {{q_graphs}} measured graphs, not the whole grammar.
  • In stage 1, 1,281 of the {{q_runs}} runs were made with 28 instead of 16 agent runs sharing a GPU. {{q_replaced}} runs that ended on the time limit under that load were run again, as was one run that failed in the engine; seven runs that went past the time limit were kept. With the {{q_replaced}} original outcomes put back, the lead of check-and-retry is unchanged and the best random graph ties check-and-retry. A check on a rerun sample of the 1,281 runs is still owed.
  • Stage 3 has five searches per way of choosing the next change, and for each seed the two ways share their first proposed change. Choosing from failures uses a hand-written table from the way a run ended to a remedy; a difference between the two ways would not by itself show that diagnosing failures helps.
